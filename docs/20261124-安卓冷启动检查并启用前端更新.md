# 安卓冷启动检查并启用前端更新

## 改动目的与原因

用户要求每次冷启动获取前端最新更新，有更新则下载并在本次启动启用。旧版 MainActivity 只调用 prepareLocal，页面 pageReady 后才后台下载并写入 ready，下一次启动才提升；页面未就绪或进程提前结束会影响下载。因此即使远端已有更新，本次仍启动旧本地页面。

## 主要内容

- Android 壳升级至 1.4.3 / versionCode 14。新建 Activity 时在后台线程执行 prepare，先恢复可用本地包，再请求签名清单、下载和校验，最后才创建本机资源服务及 Gecko 页面。本次启动直接使用新候选，原生启动页显示阶段与下载进度。
- 移除页面就绪后和 onStart 中的后台 Web 更新触发；已有页面从后台恢复不重载，不影响正在编辑的文档。APK 官网版本提醒机制不变。
- 保留签名、逐文件校验、壳与桥接兼容、固定 API 与同源检查以及候选确认、失败回退规则。远端失败时保留已验证的旧 ready 候选；切换候选前完成验证及 pending 持久化。
- 私有本机来源继续提供资源，资源可以是已下载签名包，并不等同于始终使用 APK 基线。旧 APK 必须覆盖安装一次新壳，此修复不能单靠 Web 热更新下发。

## 实际验证

- 线上签名清单 HTTP 200，通过仓库公钥 RSA-SHA256 验证；检查时发布号为 1795448225279，Web 5.3.0，最低壳代码 11。仅只读检查，未部署线上。
- `node scripts/build.mjs`：共享 Web 类型检查、Vite 构建、签名热更新打包、三架构 assembleDebug 和 lintDebug 成功。本批 Web 发布号 1795501443790，签名、ZIP 字节数及 SHA-256 匹配。
- `gradlew.bat :app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=love.imcn016.photo.WebUpdateInstrumentedTest --console=plain`：PhotoNini_API28 / Android 9 模拟器 9 项测试通过，0 失败、0 跳过。覆盖每次冷启动请求并同次启用、无新版本、旧 ready 包及远端失败、篡改、回退、本机资源授权和会话持久化等。
- 首次同时执行安卓构建和测试造成 dex 中间文件冲突，首次测试失败；构建完成后串行重跑上述测试成功。最终结果以重跑报告为准。
- 官网 `VITE_ANDROID_BUNDLED_DOWNLOADS=true pnpm build` 成功，包含 1.4.3 ARM64/ARMv7 APK、校验文件及 versionCode 14 发布记录；官网类型、双语及配置检查通过。
- ARM64 APK 经 apksigner 验证，为 Android Debug 签名；非正式发布签名。其余架构使用同一构建签名配置，交付前逐包验证。
- SDK 37.2 超出当前 AGP 已测试范围的提示、前端大 chunk 提示及 Gradle 弃用提示仍存在，不影响本次构建结果。

## 交付与限制

本批交付目录为 `artifacts/20261124-142421/`，包含三架构调试签名 APK ZIP、业务 Web ZIP（含完整签名 android-updates）、官网 ZIP、README 与 SHA256SUMS。压缩完整性和摘要验证结果以该目录部署说明为准；产物不提交 Git。

需先部署业务 Web 的不可变更新包，再部署其 latest.json；官网部署完整新包。已有用户覆盖安装与原签名兼容的 1.4.3 APK 后，冷启动策略才生效。无数据库迁移或后端改动。PC、iOS、微信小程序未改动，不单独发布安装包。

未执行生产上传、部署、线上安装或真机验收，未验证 iOS/PC/小程序运行；模拟器合成 TLS 夹具不等同于真实设备网络和生产账号验证。断网、下载或校验失败仍进入本地可用版，不保证离线获得最新版；最低壳不兼容或已被标记启动失败的发布不会强行启用。正式签名安装包未交付。
