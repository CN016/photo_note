# 灵感图文件大小

## 改动目的

在灵感图记录中保存图片最终占用的字节数，供客户端展示和后续业务查询使用；数值必须对应服务端压缩后实际存储的内容。

## 主要内容

- `inspirations` 新增可空 `file_size bigint` 字段，并通过独立增量迁移添加中文字段注释，不修改历史 SQL。
- 灵感图创建或提交 `image_key` 更新时，服务端在图片压缩和必要的原位覆盖完成后，以最终字节长度写入 `file_size`；未更改图片 key 的局部更新保留原大小。
- 非 storekey 图片和历史数据的大小保持为空；响应 DTO 返回 `file_size`，客户端不能通过请求体指定该值。
- PostgreSQL 启动 schema 检查要求存在 `file_size`，并提示按顺序执行文件元数据迁移和大小迁移。
- 更新后端部署说明和 V1 接口设计文档，说明单位、空值语义和升级步骤。

## 验证方式及结果

- `gofmt` 和 `go build ./...` 成功；`go test ./...` 成功（当前各 Go 包没有测试文件）；`go vet ./...` 和 `git diff --check` 通过。
- 在本地 PostgreSQL 17 应用 `000006` 迁移，确认 `file_size` 类型为 `bigint`，字段中文注释存在，项目 schema 外键数量为 0。
- 重建并重启 API 容器，`/healthz` 返回 `ok`。真实 HTTP 上传、创建、更新和下载流程通过：创建时 1,600×1,600 PNG 压缩后为 993,808 字节，更新后为 994,024 字节；创建和更新响应值分别与下载长度一致，数据库更新值与 994,024 一致。
- 已通过退出接口撤销验收会话，并删除本次生成的灵感图、用户和两个本地测试文件；数据库清理后均为 0 条。

## 尚未验证的内容或已知限制

- 旧记录无法从数据库还原文件大小，升级后保留 `NULL`，需客户端重新提交有效 storekey 才会补齐。
- 尚未接入的 OSS 存储后端无法读取文件，因而不能计算其哈希或文件大小。
