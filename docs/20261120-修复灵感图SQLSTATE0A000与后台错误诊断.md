# 修复灵感图 SQLSTATE 0A000 与后台错误诊断

## 改动目的

处理生产 `error_logs` 中两类问题：

- `GET /api/v1/inspirations` 与详情接口在数据库迁移增列后返回 HTTP 503，底层为 PostgreSQL SQLSTATE `0A000`。
- 每晚灵感图后台任务失败只记录 `inspiration_processing_failed`，真实异常被统一替换，无法判断具体图片处理根因。

## 主要内容

- PostgreSQL 连接固定使用 pgx 简单协议。扩展协议会缓存预编译语句及结果列描述；`inspirations` 增加 `auto_tags` 等列后，旧连接复用 `SELECT *` 可能触发 `cached plan must not change result type`（SQLSTATE `0A000`）。简单协议不复用该结果描述，迁移后不需要依赖 API 恰好同时重启。
- 灵感图后台任务 `capture` 保留原始异常，由错误日志层生成脱敏摘要；不再用固定错误码覆盖真实原因。
- 错误日志去重键加入脱敏原因摘要。相同调用位置的同类原因一分钟内仍合并，不同根因不会因恰好使用同一种 Go 错误类型而被覆盖。
- 新增独立 PostgreSQL 回归测试：先通过扩展协议生成查询缓存，再增列确认 `0A000`，最后验证应用简单协议连接仍可读取新增列。
- 后端版本从 `4.11.0` 增至 `4.11.1`。

## 验证方式及结果

- 临时 PostgreSQL 17 容器按顺序应用 `000001` 至 `000030` 全部迁移，成功。
- 设置独立测试库 `PHOTO_NINI_TENANT_TEST_DSN` 后执行 `go test ./... -count=1`，全部通过；数据库、store、HTTP API 和 service 集成测试实际运行。
- `TestPostgresSimpleProtocolSurvivesColumnAddition` 通过，确认增列后的 `0A000` 与简单协议恢复路径。
- `TestInspirationCapturePreservesSafeCause`、`TestBackgroundErrorRedactsSecrets`、`TestErrorLogDedupSeparatesCauses` 通过。
- `go vet ./...` 通过。

## 尚未验证或已知限制

- 本地验证使用临时 PostgreSQL 17 与合成数据，未连接生产库，也未执行生产部署。
- 新错误原因要等 `4.11.1` 部署后再次发生同类后台失败时才会以真实 `cause_message` 写入；本次没有拿到历史任务的具体图片 key，不能声称历史夜间失败根因已经定位。
- 历史 `0A000` 行不会回写为已解决；线上部署后应观察灵感图列表和详情接口不再新增该错误。
