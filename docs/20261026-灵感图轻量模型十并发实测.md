# 灵感图轻量模型十并发实测

## 目的与结论

验证灵感库上传后的异步人物检测，能否在 Docker 限制为 2 核 CPU、2 GiB 内存时承受最高 10 个并发推理任务，并在 10 秒内完成十张图。2026-10-26 本机实测 Nano 和 Tiny 的八个场景全部通过：每场景 11 批、每批 10 张，共 880 次图片处理，最慢一批为 2.428 秒；所有场景的十任务处理区间均存在十任务重叠，推理调用峰值也都达到十。

这次是独立模型性能验证，没有给业务 API 接入识别，没有修改现有两个压缩 worker；每日存图目标、提醒、热力图和分类浏览也不在本次交付中。后端版本按规范由 4.1.0 递增为 4.1.1，标记本批后端基准工具与构建配置改动，不表示识别功能已经上线。

## 环境、输入和计时范围

- Docker Server 20.10.17，Linux x86_64 容器；CPU 为 Intel Xeon E5-2680 v2 @ 2.80GHz。
- 限制命令：`--cpus=2 --cpuset-cpus=0,1 --memory=2g --memory-swap=2g --network=none`。容器内证据：CPU quota/period 为 200000/100000，可用 CPU 为 0-1，内存及内存加 swap 上限均为 2147483648 字节，禁止借用 swap。此处 Docker `2g` 是 2 GiB。
- 镜像 ID：`sha256:02ccb7f267bc5a9307a56c985e796d380234681c54e3fd0f36a7ec31abb9c6e3`。基础镜像固定摘要，Python 3.11、ONNX Runtime 1.23.2、OpenCV 4.12.0、NumPy 2.2.6，CPU Execution Provider。
- 使用官方 YOLOX Nano（3,659,407 字节）与 Tiny（20,219,662 字节）ONNX 权重，输入均为 416×416。各推理内部线程数为 1，同时放行 10 个 Python worker，不合并为一个 batch 输入、不用随机张量代替图片。
- 十张互不相同的 COCO val2017 公开 JPEG，包含室内、街道、动物、滑雪、运动、多人合影；另将同样十张图放大为 4000×3000 JPEG，专门压测解码和内存。放大图不是十张原生高分辨率摄影作品，不能用来评估高分辨率准确率。
- 整批计时包含释放线程屏障、本地文件读取、图片解码、缩放、模型推理、人物过滤与 NMS，到十张全部处理完成。模型初始化单独记录；首次批次未进行模型预热。未计入上传、压缩、HTTP、数据库保存和真实业务队列等待。

## 实测结果

每行 11 批；内存列为 cgroup 峰值，单位 MiB。共享模型表示十线程并发调用同一个 ONNX Session；独立模型表示十个 worker 分别持有一个 Session，均为同一容器内线程，不是十个独立 Python 进程。

| 模型 | 模型加载方式 | 图片 | 十张整批耗时范围 | 容器峰值内存 |
|---|---|---|---:|---:|
| Nano | 共享模型 | 普通图 | 0.443–0.511 秒 | 175.6 MiB |
| Nano | 共享模型 | 1200 万像素放大图 | 0.880–1.216 秒 | 751.3 MiB |
| Nano | 每 worker 独立模型 | 普通图 | 0.447–0.604 秒 | 261.7 MiB |
| Nano | 每 worker 独立模型 | 1200 万像素放大图 | 0.904–1.382 秒 | 825.6 MiB |
| Tiny | 共享模型 | 普通图 | 1.211–1.473 秒 | 253.9 MiB |
| Tiny | 共享模型 | 1200 万像素放大图 | 1.699–2.187 秒 | 816.6 MiB |
| Tiny | 每 worker 独立模型 | 普通图 | 1.208–1.446 秒 | 552.7 MiB |
| Tiny | 每 worker 独立模型 | 1200 万像素放大图 | 1.864–2.428 秒 | 1119.4 MiB |

所有场景的 cgroup v1 `memory.failcnt` 为 0，进程正常退出，没有遇到内存不足或任务失败。最重场景进程峰值 RSS 为 1154.1 MiB，与 cgroup 峰值是不同计量口径，不能相加。模型初始化加首次批次最慢为 3.019 秒，仍不包含容器启动和 Python 导入。大图少数批次实际推理调用峰值为 9（其余线程仍处于解码阶段），完整图片处理任务峰值仍为 10；普通图每批推理调用峰值均为 10。

八场景摘要、逐批耗时、环境限制、模型与输入 SHA-256、原始报告摘要见 [结构化结果](benchmarks/20261026-灵感图人物检测十并发.json)。逐图原始报告保留在被 Git 忽略的 `backend/dist/inspiration-benchmark/`，不提交模型、图片或镜像。

## 选型建议与尚未验证

就本次性能结果，优先采用 Nano + 一个共享 ONNX Session + 最高十个异步 worker，保留单次推理一个计算线程。相比每 worker 加载模型，共享 Session 可以明显减少内存。任务中仍需保留 orgid、用户 UUID、图片 key 与异步代次，图片替换、删除后不能让过期任务覆盖新结果；业务接入后再验证这些行为，本次工具不负责它们。

这次没有标注真值，无法给出人物计数准确率；两种模型对部分图片人数判断不同，不能仅根据模型大小或公开 COCO 总体指标认定 Tiny 更适合。仍需用有人工标注的摄影样本验证背影、远景、遮挡、拥挤、镜面及海报人物，并允许人工纠正。未检测到人物不代表保证无人，识别失败不能归为人数零。

2 核 2 GiB 限额仅作用于模型测试容器，不代表 Go API、压缩、数据库与 Redis 共用整机同样资源时的结果。仍需在最终低配服务器及真实业务容器组合下联合压测；不同 CPU、磁盘、图片格式与分辨率会改变耗时。当前结果证明本机所测输入下的十并发可行性，不作为任意负载下 10 秒的服务承诺。PC、Android、iOS、小程序和业务 Web 页面本批均未验证。
